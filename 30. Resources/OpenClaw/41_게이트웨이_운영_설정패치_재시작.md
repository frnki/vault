# 41. 게이트웨이 운영: 설정 패치/재시작/업데이트 안전관리 (`gateway`)

## 1) 왜 이 기능이 중요한가 (dgng 운영 맥락)
OpenClaw에서 **Gateway는 ‘운영 런타임’**입니다. dgng를 굴리다 보면 알림 채널/토큰 변경, 크론 작업 추가, 모델/세션 정책 조정 같은 “작은 설정 변화”가 계속 생깁니다. 이때 수동으로 파일을 건드리고 재기동하면 **실수·다운타임·설정 유실**이 잦아집니다. `gateway` 도구를 쓰면 **현재 설정을 안전하게 확인(config.get) → 최소 변경만 적용(config.patch) → 자동 재시작** 흐름으로 운영 리스크를 크게 줄입니다.

## 2) 핵심 개념 (간결)
- `config.get`: 현재 동작 중인 Gateway 설정을 읽기
- `config.schema`: 가능한 설정 키/형식 확인(문서 대신 “정답지”)
- `config.patch`: **부분 변경**(권장). 기존 설정에 merge 후 재시작
- `config.apply`: **전체 교체**(위험). 큰 리팩터링/마이그레이션 때만
- `restart`: 설정 변경 없이 재기동(장애 복구/누수 의심 시)
- `update.run`: OpenClaw 자체 업데이트(사용자가 명시적으로 요청할 때만)

## 3) 실전 예시 (3~5개)
### 예시 1) 현재 설정 확인(변경 전 스냅샷)
```bash
openclaw gateway status
```
```js
// (에이전트에서) 현재 설정 읽기
await gateway({ action: "config.get" })
```

### 예시 2) 스키마로 ‘가능한 키’ 먼저 확인
```js
await gateway({ action: "config.schema" })
```

### 예시 3) 안전한 부분 패치 + 재시작(권장 패턴)
```js
await gateway({
  action: "config.patch",
  note: "dgng 운영: 텔레그램 알림 라우팅/스케줄 조정",
  config: {
    patch: {
      // 예: 크론/채널 관련 설정 일부만 수정(키는 스키마에 맞춰 작성)
    }
  }
})
```

### 예시 4) 장애 시 ‘이유 포함’ 재시작(운영 로그 남기기)
```js
await gateway({ action: "restart", reason: "dgng: 채널 연결 불안정 의심, 재기동" })
```

### 예시 5) 변경 후 즉시 검증(대시보드/잡 상태)
```bash
openclaw status
openclaw gateway status
```

## 4) dgng 즉시 적용 템플릿
**변경 요청 들어오면 아래 순서로만 처리:**
1) `config.get`로 현 상태 백업(텍스트로 메모)
2) `config.schema`로 키/형식 확인
3) `config.patch`로 **최소 변경** 적용 + note 작성
4) `openclaw gateway status`로 살아있는지 확인
5) 관련 기능(크론/메시징/세션) 1회 “실제 실행”으로 확인

## 5) 함정 및 주의사항
- `config.apply`는 전체 교체라서 **누락 1개로 서비스가 죽을 수 있음** → 정말 필요할 때만.
- 패치는 “된다/안된다”가 아니라 **스키마 정합성** 싸움입니다. 키 이름 헷갈리면 항상 `config.schema`부터.
- 재시작 직후엔 연결 재협상/캐시 워밍업이 필요할 수 있어, **즉시 테스트 호출**을 습관화하세요.
- 업데이트(`update.run`)는 운영 시간대 피하고, 롤백 플랜/변경점 확인 후.

## 6) 👨‍🏫 선생님의 통찰
운영 자동화는 ‘기능 추가’보다 **변경 관리(change management)**가 더 중요합니다. dgng가 커질수록 “설정 1줄”이 장애 원인이 됩니다. `config.get → schema 확인 → patch → 검증`을 고정 루틴으로 만들면, OpenClaw는 단순한 봇이 아니라 **재현 가능한 운영 시스템**이 됩니다.
